## 1. Overview

Fiona's Slack app (`apps/fiona-slack`) records every interaction and
feedback click to Azure Cosmos DB. `apps/usage-report-function` turns that
raw telemetry into four things, each covered in its own section below:

1. A weekly KPI summary posted to Slack (§3).
2. An on-demand narrative executive PDF (§4).
3. Multi-week longitudinal trend analysis (§5).
4. An automated link from (1) to (2), generated without any manual step
   (§6).

The original goal (2026-03-20) was simply "measure user engagement — how
many people use Fiona, how frequently, how deeply, and their satisfaction
level with responses" via a weekly Slack post. Everything else in this doc
grew from executives needing a richer, presentable artifact than a Slack
text block could provide, without reintroducing the manual
notebook-and-CSV process that predated all of this.

### 1.1 Design Principles (carried through every phase)

- **One data layer, many outputs.** The same `lib/*.js` query functions
  back the Slack text report, the PDF, longitudinal trend analysis, and ad
  hoc agent queries. KPI math is never duplicated per output format.
- **No new deployed infrastructure unless justified.** Every phase that
  needed heavier compute (PDF rendering, longitudinal queries) was kept out
  of the deployed Consumption-plan Function — run ad hoc via the agent, or
  (for the automated link) via GitHub Actions — rather than upgrading the
  Function's hosting plan.
- **Deterministic, non-interpretive report text.** Narrative bullets in the
  PDF are template-filled facts (a peak value, a total, a rate), never
  LLM-authored prose. Feedback content is restated verbatim, never
  paraphrased or re-classified — sentiment is always the raw thumbs rating.
- **Graceful degradation.** A missing Cosmos/Key Vault config, a missing or
  stale report link, an empty date range — every phase degrades to a
  smaller but still-correct report rather than failing outright.

## 2. Data Recording (Cosmos DB `interactions` container)

Full current schema, retention, and privacy details are documented as the
Fiona Slack app's own behavior in
[Fiona Slack PRD §2.5, §2.7](../fiona-slack-prd.md); this section only
records the *design decisions* behind that schema, made when this
subsystem was first built (2026-03-20).

- **Partition key:** `MultiHash` on `[/deploymentType, /userId]` — chosen
  to optimize both reporting queries that filter by environment and
  distribution of data across users.
- **Retention:** No TTL on `interactions` (unlimited retention, for
  long-term trend analysis) — unlike the `feedback` container, which
  purges after 90 days (parent PRD §2.5).
- **Index policy:** Composite indexes on `(userId, timestamp)` (user-level
  trend analysis), `(threadTs, messageTs)` (session reconstruction),
  `(status, timestamp)` (error-rate queries), and two three-field
  composites covering `(timestamp, status, rateLimited)` and
  `(timestamp, rateLimited)` for the KPI queries that filter on all three.
- **Privacy:** Message content is deliberately excluded from
  `interactions` (metadata only); it's captured in `feedback` only when a
  user explicitly opts in via the feedback buttons.

## 3. Weekly KPI Slack Report

`WeeklyReportTrigger` (Azure Functions TimerTrigger, `apps/usage-report-function`)
queries the past 7 days by default and posts a KPI summary to Slack via
incoming webhook.

```none
📊 *Fiona Usage Report* — Week of Mar 10–16, 2025

👤 Unique users:           42 (🔁 27 returning, 64.3% repeat rate)
🆕 New users:              15 (35.7% of unique users)
💬 Sessions:               118
📨 Total interactions:     347
⛔ Errors:                 8 (2.3% error rate)
🚫 Rate-limited:           6

👍 Good feedback:          29
👎 Bad feedback:           7
📈 Feedback ratio:         80.6% positive
📊 Avg interactions/user:  8.3
📝 Feedback response rate: 9.8%

_Environment: production | Generated by Fiona Analytics_

📎 Full executive report: <link, when available — see §6>

📋 Representative Feedback
...
```

| Metric                    | Formula / source                                                                |
| -------------------------- | ---------------------------------------------------------------------------------|
| Distinct users              | Count of unique users with successful interactions                              |
| New users (count & %)        | No prior successful interaction before the window; `newUsersCount / distinctUsers * 100` |
| Returning users & repeat rate | Derived: `distinctUsers - newUsersCount`, `100 - newUserPercentage`            |
| Sessions                    | Distinct `threadTs` across successful, non-rate-limited interactions            |
| Total interactions           | All interactions (success + error) in the window                              |
| Error rate                  | `errorCount / totalInteractions * 100` (0 if no interactions)                   |
| Rate-limited hits             | Count of rate-limiter blocks                                                   |
| Feedback ratio               | `good / (good + bad) * 100` (0 if no feedback)                                 |
| Avg interactions / user        | Mean interactions per active user                                             |
| Feedback response rate        | Feedback count / successful-interaction count                                  |
| Representative feedback       | Up to 5 examples, reason-prioritized (§7)                                      |
| Report link                  | §6                                                                              |

**Configuration:** `REPORT_SCHEDULE` (cron, default `0 9 * * 1`),
`COSMOS_ENDPOINT`/`COSMOS_DATABASE`/`COSMOS_INTERACTIONS_CONTAINER`/`COSMOS_FEEDBACK_CONTAINER`,
`DEPLOYMENT_TYPE`, `KEY_VAULT_URL` + `SLACK_WEBHOOK_KEYVAULT_SECRET_NAME`
(webhook retrieved via Managed Identity at runtime). Full current list,
including §6's additions: [Usage Report PRD §5](../usage-report-prd.md#5-environment-variables).

**Error handling:** transient Cosmos/network failures retry with
exponential backoff (up to 3); configuration errors (missing secrets/env
vars) log and fail fast; a failed Slack POST logs to Application Insights;
occasional duplicate reports on retry are accepted rather than
de-duplicated.

> [!NOTE]
> AI-141 also calls for new-user/returning-user metrics to appear in the
> trend report that accompanies the Sprint report. That trend-report
> integration is not yet built.

## 4. Executive PDF Report

### 4.1 Rendering Approach: Puppeteer + HTML/CSS + Chart.js (current)

A first implementation rendered the PDF with `pdfkit` — hand-drawn vector
charts and tables, no Chromium dependency, chosen specifically because that
concern (a ~300MB Chromium download, sandboxing) had ruled out this
approach for the *deployed Function*. Two real bugs were found and fixed
before it was retired: text wrapping past its allotted box bled into
whatever rendered next, in both chart axis labels and table cells — both
symptoms of the same root cause, that pdfkit has no CSS-style box model, so
every wrap/overflow decision was manual arithmetic.

A later redesign replaced the report's *structure* (six small charts per
section, wide raw-data tables dominating every page) with a narrative,
executive-readable format (KPI cards, one enlarged trend chart, prose
"Readout" insights, feedback as cards, detailed tables relegated to an
appendix) — and that harder rendering job (a dual-axis combo chart, rounded/
shadowed cards, rotated axis labels) made pdfkit's overflow-bug risk worse,
not better. Three approaches were considered for the new renderer:

1. **Extend pdfkit further** — no new dependencies, but the combo chart and
   card styling need substantial hand-rolled vector math, and the
   underlying overflow risk remains.
2. **Puppeteer + HTML/CSS + Chart.js** *(chosen)* — CSS handles wrapping/
   overflow/rounded-corners/shadows/grid layout natively; Chart.js handles
   the combo chart, legends, and rotated labels with no custom code. Cost:
   a ~300MB Chromium dependency and a new failure surface (sandboxing, font
   availability, browser lifecycle) — but the Chromium safety concern that
   ruled out this approach for the *deployed Function* specifically doesn't
   apply here, since this path only ever runs ad hoc (via the agent, or via
   GitHub Actions for §6) — never inside the deployed Function.
3. **Python (matplotlib + reportlab)**, matching the original notebook
   stack — would nail the reference PDF's exact visual style with the
   least custom code. Rejected because it reverses the stated purpose of
   porting logic into JS "so the same query helpers... can also answer
   this without the manual notebook process" — reintroducing Python here
   means a second language/runtime wherever the agent or CI runs, and an
   ongoing split between JS query-layer maintainers and Python
   rendering-layer maintainers.

**Dependencies:** `puppeteer`, `chart.js` (loaded from local `node_modules`
at render time, not a CDN — generation never depends on network access).
`pdfkit` was removed.

### 4.2 Data-Slice Architecture

Each report section is an independent data slice — a plain array of
objects, no shared intermediate state — fetched by its own query function
and handed to its own renderer. Each slice stays independently testable.

| Section                       | Data source                                                             |
| ------------------------------- | -------------------------------------------------------------------------|
| KPI summary                      | `getKpiSummary` (`lib/kpi-summary.js`)                                  |
| Week-over-week trends             | `getWeeklyTrendSeries` (`lib/longitudinal-queries.js`, §5)             |
| Weekly snapshots (appendix)         | Same `getWeeklyTrendSeries` output, reshaped (no WoW columns)         |
| Daily summary                     | `getDailySummary` (`lib/daily-queries.js`)                             |
| Feedback details (appendix)          | `getFeedbackDetails` (`lib/cosmos-queries.js`) — chronological, unfiltered |
| Representative feedback (cards)      | `getRepresentativeFeedbackInRange` (`lib/cosmos-queries.js`, §7)      |
| Top users by feedback / interactions   | `getTopUsersByFeedback` / `getTopUsersByInteractions` (`lib/user-queries.js`) |

`getDailySummary` additionally tracks `newUsers`/`returningUsers`/`repeatRate`
per day, mirroring `getWeeklyTrendSeries`'s logic: bucket each user's
first-seen-in-range day, then reuse one prior-history query (not per-day)
to classify true new vs. returning.

`buildExecutiveReportData` (`lib/report-data.js`) runs all of the above in
parallel and returns one plain object — `period`, `kpiSummary`,
`weeklyTrend`, `trendWeekly` (a wider rolling window for historical
context, snapped to Monday boundaries), `dailySummary`, `feedbackDetails`,
`representativeFeedback`, `topUsersByFeedback`, `topUsersByInteractions`.
No formatting/rendering logic lives here — the same separation of concerns
as `getWeeklyTrendSeries` vs. `formatLongitudinalReport`.

### 4.3 Rendering Pipeline

- **`lib/pdf/narrative.js`** — pure functions computing deterministic,
  template-based text from `reportData`. No AI-authored/interpretive
  prose; every sentence is a fixed template filled with a computed fact.
  Exports `buildReadoutBullets`, `buildUsageObservations`,
  `buildReliabilityTakeaways`.
- **`lib/pdf/report-template.js`** — `renderExecutiveReportHtml(reportData,
  narrative, chartJsSource)` returns a full HTML document string (inline
  `<style>`, Chart.js `<canvas>` elements, KPI/feedback card markup,
  appendix tables).
- **`lib/pdf/generate-executive-report-pdf.js`** —
  `generateExecutiveReportPdf(reportData, outputPath)`: computes narrative
  → renders HTML → launches Puppeteer (`--no-sandbox --disable-gpu
  --disable-dev-shm-usage`, required for this environment's Chrome
  sandboxing) → sets page content → waits for
  `window.__chartsReady === true` (Chart.js `animation: false` plus an
  `onComplete` signal, not a fixed delay) → prints to PDF with a
  `footerTemplate` (environment, period, page numbers) → writes the file.

**Page-by-page mapping:**

| Page | Content |
|---|---|
| 1 — Cover / Executive Summary | Title; period/environment/generated header; 2×3 KPI card grid; Readout bullets |
| 2 — Usage Trends | One enlarged combo chart (bar: Interactions; lines: Users, Sessions; dual y-axis); observation table |
| 3 — Reliability and Feedback | Weekly error-rate bar chart; weekly feedback-volume stacked bar chart; takeaway table |
| 4 — Representative Feedback | Cards (colored by sentiment), `Q:`/`A:` verbatim (truncated, never paraphrased) |
| 5 — Top Users | Top users by feedback (5 rows), by interaction count (6 rows) |
| 6 — Appendix | Weekly snapshot table; daily summary charts + table; executive notes |

Footer on every page: `Fiona Usage Analytics | {environment} | {period}`
and `Page X of Y`.

**This entire rendering path runs ad hoc only** — invoked by the
`azure-usage-report` agent skill, or by the GitHub Actions workflow in §6
— never by the deployed `WeeklyReportTrigger` Function.

## 5. Longitudinal Trend Analysis

`getWeeklyTrendSeries` (`lib/longitudinal-queries.js`) answers "how has
usage trended over the last N weeks" without the manual notebook process
that predated it. Two data-fetching approaches were considered: looping
the existing single-week helpers once per week boundary (simple, but ~9
queries × N weeks — expensive as the range grows), versus fetching raw
records for the full range once per container and bucketing into weeks in
JS (query cost stays flat regardless of range length; mirrors what the
notebook already did with pandas `groupby`). **Chosen: the latter.**

- Fetches raw interaction/feedback documents for `[startISO, endISO)` in
  two queries (plus one bounded prior-history query for new/returning-user
  classification), buckets into Monday–Sunday weeks.
- Per week: `uniqueUsers`, `sessions`, `totalInteractions`, `errors`,
  `errorRate`, `rateLimited`, `goodFeedback`, `badFeedback`,
  `feedbackRatio`, `avgInteractionsPerUser`, `feedbackResponseRate`,
  `newUsers`, `returningUsers`, `repeatRate`.
- Week-over-week deltas (`usersWowPct`, `interactionsWowPct`,
  `errorRateWowPp`) between consecutive weeks; `null` for the first week
  (no prior week to diff against).
- Returns plain data with no formatting baked in, so both the Slack
  formatter and the PDF renderer consume the same structure.

`formatLongitudinalReport` (`lib/slack-formatter.js`) renders this as one
Slack-text block per week, reusing `formatWeeklyReport`'s emoji/line style,
each block including a WoW delta line (skipped for the first week).

**Agent ground rule:** for requests spanning more than one week, use this
module instead of looping single-window helpers — the longitudinal query
fetches raw records for the whole range once, so looping would multiply
query cost unnecessarily. `getWeeklyTrendSeries` buckets by Monday–Sunday
calendar week; if a requested range isn't already week-aligned, snap it
outward to the nearest Monday/Sunday before calling it, or call out that
the edge week(s) are partial.

## 6. Automated Executive Report Link

The deployed Function posts a text-only KPI summary; the PDF (§4) has
always run ad hoc only. This closes that gap: every Monday's Slack message
includes a link to that week's PDF, generated automatically with no
manual/agent step, and without changing the Function's hosting plan.

**Approaches considered:**

1. **Move PDF generation into the deployed Function, upgrade its hosting
   plan** (Premium/Elastic Premium) to tolerate Puppeteer's Chromium
   footprint. Rejected: real infra/cost change, and reverses the specific
   reason Chromium was kept out of the Function (§4.1).
2. **Render a lighter, Chromium-free report** for the automated link,
   keeping the rich PDF agent-only. Rejected: a materially worse artifact
   than the PDF already designed and reviewed, just to avoid Chromium.
3. **Generate the PDF in a scheduled GitHub Actions workflow, host it in
   Blob Storage, link to it from the unchanged Function** *(chosen)*.
   GitHub's `ubuntu-latest` runners have no Consumption-plan-style Chromium
   constraint, so the existing PDF pipeline (§4) runs completely
   unmodified. The Function stays the sole owner of "what gets posted to
   Slack" — no duplicated KPI-formatting logic in two places.

### 6.1 Architecture

```
GitHub Actions (generate-usage-report-pdf.yml, cron a few hours before
REPORT_SCHEDULE, plus workflow_dispatch)
  → scripts/generate-executive-report-artifact.js computes the same
    [oneWeekAgo, endOfReport) window WeeklyReportTrigger uses, then calls
    buildExecutiveReportData + generateExecutiveReportPdf (§4, unmodified)
  → az storage blob upload the PDF to fionausagereportsa / usage-reports,
    per-week blob name
  → az storage blob generate-sas (--as-user, AAD user delegation, no
    shared account key) for that blob
  → write/overwrite usage-reports/latest-link.json:
      { url, weekStart, weekEnd, deploymentType }

WeeklyReportTrigger (unchanged Consumption-plan Function, existing schedule)
  → computes KPIs (unchanged, §3)
  → lib/report-link.js#getLatestReportLink reads latest-link.json via
    the Function's managed identity (Storage Blob Data Reader on the
    container)
  → if the pointer's weekEnd + deploymentType match this run's window
      → append a link line to the Slack message
    else
      → post KPI text only, log a warning
  → posts one Slack message (unchanged webhook call)
```

The PDF and KPI text intentionally describe the *same* Mon–Sun window — the
GitHub Actions cron runs shortly before `REPORT_SCHEDULE`, not a multi-day
buffer, specifically to keep both computing the same range. A same-window
mismatch (job didn't finish, failed, or drifted) is handled by simply
omitting the link that week, not by blocking or retrying the Slack post.

### 6.2 New Files

- **`lib/report-link.js`** — `getLatestReportLink({ deploymentType,
  weekEnd }, logger)`. Reads the pointer via `@azure/storage-blob`; returns
  the URL only on a matching window, `null` otherwise. Never throws — any
  storage/parse failure or window mismatch degrades to `null` plus a
  `logger.warn(...)`, so a storage problem never blocks the KPI Slack post.
- **`scripts/generate-executive-report-artifact.js`** — the workflow's
  Node entry point. Computes the lookback window, calls
  `buildExecutiveReportData` + `generateExecutiveReportPdf` unmodified,
  writes the PDF plus a `report-meta.json` the workflow's later `az` CLI
  steps read.
- **`.github/workflows/generate-usage-report-pdf.yml`** — the scheduled
  workflow. Auth via a dedicated service principal (`Cosmos DB Data
  Reader` on the `chatbot` database, `Storage Blob Data Contributor` +
  `Storage Blob Delegator` scoped to the `usage-reports` container only).

### 6.3 Changed Files

- **`lib/slack-formatter.js`** — `formatWeeklyReport` appends an optional
  `📎 *Full executive report:* <url>` line when `reportUrl` is present;
  omitted entirely when absent.
- **`WeeklyReportTrigger/index.js`** — calls `getLatestReportLink` before
  formatting the message and passes the result through as `reportUrl`.

### 6.4 Storage Layout

- Container `usage-reports` in the `fionausagereportsa` account (the same
  account backing `usage-report-function`'s `AzureWebJobsStorage`, in
  `edfi-fiona-rg`). Note: `DEPLOYMENT.md` elsewhere in this repo uses
  `fionastorage`/`fiona-rg` as *generic placeholder names* in unrelated
  example commands — the real resource names discovered while setting
  this up are `fionausagereportsa` and `edfi-fiona-rg`.
- Per-week PDFs: `executive-report-<deploymentType>-<start>-to-<end>.pdf`,
  matching the naming convention the agent already uses for ad hoc runs.
  Kept indefinitely as an audit trail — no lifecycle/retention policy in
  this scope.
- One pointer blob, `latest-link.json`, overwritten every run.

### 6.5 SAS Lifetime Constraint (discovered during verification)

The design originally called for a long-lived (~90-day) SAS URL. While
manually verifying the upload/SAS/pointer steps end-to-end, `az storage
blob generate-sas --as-user` (Azure AD user delegation SAS, chosen so the
workflow never needs the storage account's shared key) rejected any expiry
beyond 7 days:

```
ERROR: incorrect usage: --expiry should be within 7 days from now
```

This is a hard Azure platform limit on user delegation SAS, not a
configuration choice. Fixed by using a 6-day expiry instead (leaving margin
for clock skew) rather than switching to account-key-based SAS.
Consequence: each week's report link stays reachable for about a week —
roughly through the next Monday's message — before expiring. The
underlying PDF blobs remain in storage indefinitely; only the
previously-issued SAS URL for them goes stale. Switching to account-key
SAS would restore the longer expiry but reintroduce a shared secret into
the pipeline, which the RBAC-only design was specifically chosen to avoid.

### 6.6 Error Handling / Observability

- `getLatestReportLink` never throws — degrades to KPI-text-only plus a
  `logger.warn(...)`, matching the existing failure-isolation pattern
  around `SLACK_DRY_RUN` and the handler's outer try/catch.
- GitHub Actions workflow failures surface as a failed Actions run;
  `workflow_dispatch` covers manual re-runs. No new alerting, no
  in-workflow retries — an accepted trade-off of running close to
  `REPORT_SCHEDULE` instead of days ahead.

- Storage container, dedicated service principal + role assignments

- `scripts/generate-executive-report-artifact.js` was run locally against

## 7. Representative Feedback Selection

`getRepresentativeFeedback` (`lib/cosmos-queries.js`) selects up to 5
feedback examples for the Slack report:

- Queries the `feedback` container for `[startDate, endDate)`.
- Two-tier selection: entries with a non-empty `reason` first (most recent
  first), then reason-less entries filling remaining slots (most recent
  first). Each item is tagged `hasReason: boolean`.
- Sentiment is never computed via LLM/NLP — it's derived directly from the
  thumbs rating (`good-feedback` → 👍 Positive, `bad-feedback` → 👎
  Negative). The free-text `reason`, when present, is shown verbatim — it
  is restated, not reinterpreted.

`formatFeedbackSection` (`lib/slack-formatter.js`) renders this as plain
text (no Slack Block Kit): truncates `userMessage`/`botResponse`/`reason`
independently to 150 characters each; prints `Reason: (no reason
provided)` explicitly for fallback items rather than omitting the line;
prints `No feedback recorded for this period.` when empty.

`getRepresentativeFeedbackInRange` (§4.2) is a range-bound sibling used by
the executive PDF and longitudinal/ad hoc requests: `getRepresentativeFeedback`
takes only an open-ended-to-now lower bound, which is correct for
`WeeklyReportTrigger`'s "last 7 days up to now" usage but would silently
include feedback past an arbitrary past range's `endISO`. Kept as a
separate function rather than changing `getRepresentativeFeedback`'s
signature, since that function is actively used by `WeeklyReportTrigger`
with passing tests that assume its current open-ended behavior.

## 8. Testing

Each module's tests live alongside it in `apps/usage-report-function/test/unit/`
(mirroring the module structure in [Usage Report PRD §4.3](../usage-report-prd.md#43-module-structure)).
Notable patterns, consistent across every phase above:

- Pure/deterministic functions (`narrative.js`, `format.js`,
  `slack-formatter.js`, query bucketing logic) get plain unit tests against
  known fixtures, asserting exact computed values/strings.
- Cosmos-backed query functions are tested against mocked container
  clients (`items.query().fetchAll()` mocked to return canned resources),
  never a live Cosmos instance.
- `generate-executive-report-pdf.js` has an integration-style test: a real
  Puppeteer run against fixture data, confirming a valid multi-page PDF is
  produced (slower, due to Chromium launch).
- `report-link.js` is tested against a mocked `@azure/storage-blob` client:
  matching window → URL; mismatched window / missing blob / malformed JSON
  → `null`, never throwing.
- Manual smoke tests (temp runner scripts inside `apps/usage-report-function/`,
  deleted after use) confirm real-data behavior the mocked unit tests
  can't — e.g. visual PDF review, or the `az` CLI steps in §6.

## 9. Out of Scope / Not Pursued

- **Retention/lifecycle policy** for old PDF blobs (§6.4) — revisit only if
  storage growth becomes a real problem.
- **Alerting** on GitHub Actions workflow failure (§6.6).
- **Any change to the deployed Function's hosting plan** — every phase
  above was explicitly designed around keeping it Consumption-plan.
- **"Historical Context" PDF page** (weekly trend charts since a baseline
  date, current period highlighted) — designed in detail at one point,
  then deliberately not pursued; dropped rather than carried forward as
  backlog.
- **Top users leaderboards / raw feedback-detail listings in the Slack
  report** — covered by the PDF (§4.2) and ad hoc agent capabilities, not
  the weekly Slack text itself.
- **LLM/NLP-based sentiment classification** anywhere in this subsystem —
  sentiment is always the raw thumbs rating, feedback text is always
  verbatim (§7).
